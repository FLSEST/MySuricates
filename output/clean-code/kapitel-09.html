09

Unit-Tests

Die drei Gesetze von TDD, das F.I.R.S.T.-Prinzip und warum saubere Tests genauso wichtig sind wie sauberer Produktionscode.

Z Zusammenfassung

Fuer Robert C. Martin sind Unit-Tests nicht bloss ein Qualitaetswerkzeug — sie sind die Grundlage professioneller Softwareentwicklung. In diesem Kapitel legt er dar, warum Tests denselben Qualitaetsstandards unterliegen sollten wie der Produktionscode und wie Test-Driven Development (TDD) zu besserem Design fuehrt.

Martin formuliert die drei Gesetze von TDD praezise: Erstens darfst du keinen Produktionscode schreiben, bevor du einen fehlschlagenden Unit-Test geschrieben hast. Zweitens darfst du nicht mehr von einem Unit-Test schreiben, als noetig ist, damit er fehlschlaegt — und nicht kompilieren zaehlt als fehlschlagen. Drittens darfst du nicht mehr Produktionscode schreiben, als noetig ist, um den aktuell fehlschlagenden Test zu bestehen. Dieser enge Zyklus fuehrt dazu, dass Tests und Produktionscode gleichzeitig und in kleinen Schritten wachsen.

Doch Tests zu schreiben genuegt nicht — sie muessen sauber sein. Martin hat Teams gesehen, die ihre Tests vernachlaessigten: Die Tests wurden unlesbar, schwer zu warten und schliesslich aufgegeben. Ohne Tests verloren die Teams das Vertrauen in ihren Code und hoerten auf, Aenderungen vorzunehmen. Die Codebasis verfiel. Die Lektion: Schmutzige Tests sind schlimmer als keine Tests. Tests, die nicht gewartet werden, verlieren ihren Wert und werden zur Buerде.

Saubere Tests zeichnen sich durch Lesbarkeit aus — und Lesbarkeit in Tests bedeutet Klarheit, Einfachheit und Ausdrucksdichte. Martin empfiehlt das Build-Operate-Check Pattern: Zuerst die Testdaten aufbauen (Build), dann die zu testende Operation ausfuehren (Operate), schliesslich das Ergebnis pruefen (Check). Diese klare Dreiteilung macht jeden Test auf den ersten Blick verstaendlich.

Ein weiterer wichtiger Grundsatz: Ein Konzept pro Test. Jeder Test sollte genau ein Verhalten pruefen. Tests, die mehrere unabhaengige Dinge ueberpruefen, sind schwerer zu verstehen und geben im Fehlerfall weniger praezise Hinweise. Wenn ein Test mit sechs Assertions fehlschlaegt, ist unklar, welches Verhalten tatsaechlich gebrochen ist. Einzelne, fokussierte Tests hingegen zeigen sofort, was schiefgegangen ist.

Martin fuehrt das F.I.R.S.T.-Prinzip ein, das fuenf Eigenschaften guter Tests beschreibt: Fast — Tests muessen schnell laufen, sonst werden sie nicht regelmaessig ausgefuehrt. Independent — Tests duerfen nicht voneinander abhaengen; jeder Test muss allein lauffaehig sein. Repeatable — Tests muessen in jeder Umgebung das gleiche Ergebnis liefern, ob auf dem Entwicklerrechner, im CI oder auf dem Produktionsserver. Self-Validating — Tests muessen ein klares Bestanden/Nicht-Bestanden-Ergebnis liefern, ohne dass ein Mensch die Ausgabe interpretieren muss. Timely — Tests muessen zum richtigen Zeitpunkt geschrieben werden, naemlich kurz vor dem Produktionscode, nicht lange danach.

Martin betont auch den Design-Aspekt von Tests: Code, der schwer zu testen ist, weist oft auf Designprobleme hin. Enge Kopplung, versteckte Abhaengigkeiten und globaler Zustand machen Tests schwierig. Wenn man zuerst Tests schreibt, wird man natuerlich zu besserem Design gedraengt — zu loser Kopplung, klaren Schnittstellen und injizierbaren Abhaengigkeiten. TDD ist daher nicht nur eine Testmethode, sondern ein Design-Treiber.

Abschliessend warnt Martin davor, in Tests andere Qualitaetsstandards anzulegen als im Produktionscode. Tests duerfen etwas weniger effizient sein (da Performance selten kritisch ist), aber sie muessen genauso lesbar und wartbar sein. Denn Tests sind es, die uns den Mut geben, unseren Code zu veraendern. Ohne diese Sicherheitsnetze stagniert jedes Projekt.

K Kernaussagen

1

Die drei Gesetze von TDD

Kein Produktionscode ohne fehlschlagenden Test. Nur so viel Test, wie fuer ein Fehlschlagen noetig. Nur so viel Produktionscode, wie fuer das Bestehen noetig. Dieser enge Zyklus fuehrt zu inkrementellem Wachstum.

2

F.I.R.S.T. — Fuenf Eigenschaften guter Tests

Fast (schnell), Independent (unabhaengig), Repeatable (wiederholbar), Self-Validating (selbstpruefend), Timely (rechtzeitig). Diese fuenf Kriterien definieren die Qualitaet eines Unit-Tests.

3

Tests sauber halten

Schmutzige Tests sind schlimmer als keine Tests. Testcode verdient dieselbe Sorgfalt wie Produktionscode — Lesbarkeit, Klarheit und Wartbarkeit sind essentiell.

4

Ein Konzept pro Test

Jeder Test prueft genau ein Verhalten. Fokussierte Tests geben im Fehlerfall praezise Hinweise und sind leichter zu verstehen und zu warten.

5

Testbarkeit als Design-Treiber

Schwer testbarer Code deutet auf Designprobleme hin. TDD fuehrt natuerlich zu loser Kopplung, klaren Schnittstellen und injizierbaren Abhaengigkeiten — besseres Design durch Tests.

6

Build-Operate-Check Pattern

Jeder Test folgt einer klaren Dreiteilung: Testdaten aufbauen (Build), Operation ausfuehren (Operate), Ergebnis pruefen (Check). Diese Struktur macht Tests sofort verstaendlich.

Vergleich: Ein unuebersichtlicher Test versus ein sauberer, nach dem Build-Operate-Check Pattern strukturierter Test.

Schlecht Unuebersichtlich, mehrere Konzepte, schwer zu lesen 
@Test
public void testEverything() throws Exception {
    // Alles in einem Test gemischt — Build, Operate, Check
    // durcheinander und mehrere Konzepte gleichzeitig
    String page = "<html><body>Test</body></html>";
    crawler.addPage(root, page);
    String result = crawler.crawl();
    assertNotNull(result);
    assertTrue(result.contains("Test"));
    assertEquals(1, crawler.getPageCount());
    // Noch ein voellig anderes Konzept im selben Test
    crawler.addPage(root, "<html></html>");
    result = crawler.crawl();
    assertEquals(2, crawler.getPageCount());
    assertTrue(result.contains("Test"));
    // Und noch ein drittes...
    crawler.deletePage(root);
    assertEquals(1, crawler.getPageCount());
    assertFalse(crawler.hasPage(root));
    // Welcher Assert ist fehlgeschlagen?
    // Was genau wird hier eigentlich getestet?
}
Sauber Build-Operate-Check, ein Konzept pro Test 
// Ein Konzept pro Test — sofort verstaendlich

@Test
public void crawledPageContentIsIncludedInResult() {
    // BUILD: Testdaten aufbauen
    String pageContent = "<html><body>Test</body></html>";
    crawler.addPage(root, pageContent);

    // OPERATE: Zu testende Operation ausfuehren
    String result = crawler.crawl();

    // CHECK: Ergebnis pruefen
    assertThat(result).contains("Test");
}

@Test
public void pageCountIncrementsWhenPageIsAdded() {
    // BUILD
    String page = "<html><body>Content</body></html>";

    // OPERATE
    crawler.addPage(root, page);

    // CHECK
    assertThat(crawler.getPageCount()).isEqualTo(1);
}

@Test
public void deletedPageIsNoLongerAccessible() {
    // BUILD
    crawler.addPage(root, "<html></html>");

    // OPERATE
    crawler.deletePage(root);

    // CHECK
    assertThat(crawler.hasPage(root)).isFalse();
}

// Jeder Test ist:
// - Fast: Laeuft in Millisekunden
// - Independent: Kein Test haengt von einem anderen ab
// - Repeatable: Gleiches Ergebnis auf jedem Rechner
// - Self-Validating: Bestanden oder Nicht-Bestanden
// - Timely: Geschrieben VOR dem Produktionscode

"Testcode ist genauso wichtig wie Produktionscode. Er ist kein Buerger zweiter Klasse. Er erfordert Nachdenken, Design und Sorgfalt. Er muss genauso sauber gehalten werden wie Produktionscode."

— Robert C. Martin, Clean Code, Kapitel 9
