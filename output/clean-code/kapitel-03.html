03

Funktionen

Wie man Funktionen schreibt, die klein, fokussiert und verstaendlich sind — die fundamentalen Bausteine sauberen Codes.

# Zusammenfassung

Funktionen sind die Verben einer Programmiersprache, und Klassen die Substantive. In der Kunst der Programmierung — wie in jeder Kunst der Sprache — kommt es darauf an, diese Verben und Substantive geschickt einzusetzen. Kapitel 3 widmet sich ganz der Frage, wie man Funktionen schreibt, die lesbar, wartbar und elegant sind. Es ist eines der praktischsten Kapitel des gesamten Buches.

Die allererste Regel lautet: Funktionen sollen klein sein. Und die zweite Regel lautet: Sie sollen noch kleiner sein. Martin argumentiert, dass Funktionen selten laenger als 20 Zeilen sein sollten und idealerweise nur 5-10 Zeilen umfassen. In den Anfangstagen der Programmierung galt, dass eine Funktion auf einen Bildschirm passen sollte — bei 24 Zeilen und 80 Spalten. Heute haben wir groessere Bildschirme, aber die Regel sollte strenger werden, nicht lockerer. Kleine Funktionen sind leichter zu verstehen, zu testen und zu warten.

Funktionen sollen eine einzige Sache tun. Sie sollen sie gut tun. Und sie sollen nur diese eine Sache tun. Aber wie bestimmt man, ob eine Funktion nur eine Sache tut? Martin schlaegt die folgende Heuristik vor: Wenn man eine Funktion beschreibt und dabei das Wort "und" verwendet, tut sie wahrscheinlich mehr als eine Sache. Eine weitere Pruefmethode: Kann man sinnvoll eine weitere Funktion aus ihr extrahieren, die nicht bloss eine Umformulierung der Implementierung ist?

Die Step-Down-Regel besagt, dass Code wie ein Zeitungsartikel von oben nach unten gelesen werden sollte. Jede Funktion sollte von Funktionen der naechsttieferen Abstraktionsebene gefolgt werden. So kann man den Code wie eine Erzaehlung lesen: "Um X zu tun, machen wir A, dann B, dann C. Um A zu tun, machen wir D und E..." Diese Struktur erleichtert das Verstaendnis enorm.

Eine Abstraktionsebene pro Funktion ist eng mit der Step-Down-Regel verbunden. Eine Funktion sollte nicht Operationen hoher Abstraktion (wie getHtml()) mit Operationen niedriger Abstraktion (wie .append("\n")) vermischen. Wenn beides in einer Funktion vorkommt, kann der Leser nicht unterscheiden, was wesentlicher Konzept und was Detail ist.

Switch-Anweisungen sind von Natur aus gross und tun mehrere Dinge. Martin raet, sie in abstrakten Fabriken zu verbergen, die polymorphe Objekte erzeugen. So wird die Switch-Anweisung nur einmal geschrieben, und der Rest des Systems arbeitet mit den polymorphen Interfaces. Dadurch wird der Code flexibler und leichter erweiterbar.

Beschreibende Namen sind bei Funktionen besonders wichtig. Ein langer beschreibender Name ist besser als ein kurzer raetselhafter Name oder ein langer beschreibender Kommentar. Namen wie includeSetupAndTeardownPages sind besser als includeSetups, weil sie genau beschreiben, was die Funktion tut. Konsistenz bei der Namensgebung ist ebenfalls entscheidend: Wenn man includeSetup sagt, sollte man auch includeTeardown sagen, nicht addTeardown.

Funktionsargumente: Die ideale Anzahl ist null (niladisch). Dann kommt eins (monadisch), dann zwei (diadisch). Drei Argumente (triadisch) sollten wo moeglich vermieden werden, und mehr als drei (polyadisch) erfordern eine sehr gute Begruendung. Argumente erschweren das Verstaendnis und das Testen. Jedes Argument zwingt den Leser, seinen Kontext zu verstehen. Wenn eine Funktion mehr als zwei oder drei Argumente benoetigt, sollten einige in ein eigenes Objekt zusammengefasst werden.

Keine Seiteneffekte: Eine Funktion verspricht, eine Sache zu tun, tut dann aber heimlich noch etwas anderes. Zum Beispiel eine Funktion checkPassword(), die als Seiteneffekt die Session initialisiert. Solche versteckten Nebeneffekte schaffen zeitliche Kopplungen und fuehren zu schwer auffindbaren Fehlern.

Die Command-Query-Trennung besagt, dass eine Funktion entweder etwas tun oder etwas beantworten soll — aber nicht beides. Wenn eine Funktion den Zustand eines Objekts aendert, sollte sie keinen Wert zurueckgeben. Wenn sie einen Wert zurueckgibt, sollte sie keinen Zustand aendern. Diese klare Trennung vermeidet verwirrende Konstrukte.

Exceptions statt Fehlercodes: Wenn Funktionen Fehlercodes zurueckgeben, zwingt das den Aufrufer zu verschachtelten if-Anweisungen. Try-Catch-Bloecke sind zwar haesslich, aber sie trennen den normalen Ablauf sauber von der Fehlerbehandlung. Die Fehlerbehandlung sollte in eine eigene Funktion extrahiert werden. Das DRY-Prinzip (Don't Repeat Yourself) rundet das Kapitel ab: Duplikation ist der Ursprung allen Uebels in der Software.

! Wichtige Erkenntnisse

Klein halten

Funktionen sollten selten mehr als 20 Zeilen haben. Ideal sind 5-10 Zeilen. Kleine Funktionen sind leichter zu verstehen, zu testen und zu benennen.

Eine Aufgabe

Jede Funktion soll genau eine Sache tun. Wenn man das Wort "und" braucht, um sie zu beschreiben, tut sie zu viel.

Wenige Parameter

Null Argumente sind ideal, eins ist gut, zwei akzeptabel, drei erfordern Begruendung. Mehr als drei in ein Objekt buendeln.

Keine Seiteneffekte

Funktionen sollen nur tun, was ihr Name verspricht. Versteckte Zustandsaenderungen schaffen zeitliche Kopplungen und Fehlerquellen.

Abstraktionsebenen

Jede Funktion operiert auf einer Abstraktionsebene. Die Step-Down-Regel: Von hoher zu niedriger Abstraktion, wie ein Zeitungsartikel.

DRY — Don't Repeat Yourself

Duplikation ist der Ursprung allen Uebels. Jeder Algorithmus, jede Geschaeftsregel soll genau einmal an einer Stelle existieren.

Zu grosse Funktion 
public String renderPage(PageData pageData,
    boolean isSuite) throws Exception {
  String result = "";
  if (isTestPage(pageData)) {
    WikiPage testPage = pageData.getWikiPage();
    StringBuffer buf = new StringBuffer();
    if (isSuite) {
      WikiPage suiteTeardown =
        PageCrawlerImpl.getInheritedPage(
          "SuiteTearDown", testPage);
      if (suiteTeardown != null) {
        buf.append(suiteTeardown
          .getData().getHtml());
      }
    }
    WikiPage teardown =
      PageCrawlerImpl.getInheritedPage(
        "TearDown", testPage);
    if (teardown != null) {
      buf.append(teardown
        .getData().getHtml());
    }
    // ... 30 weitere Zeilen ...
    pageData.setContent(buf.toString());
    result = pageData.getHtml();
  }
  return result;
}
Kleine, fokussierte Funktionen 
public String renderPage(
    PageData pageData) throws Exception {
  if (isTestPage(pageData))
    includeSetupAndTeardownPages(pageData);
  return pageData.getHtml();
}

private void includeSetupAndTeardownPages(
    PageData pageData) throws Exception {
  includeSetupPages(pageData);
  includePageContent(pageData);
  includeTeardownPages(pageData);
}

private void includeSetupPages(
    PageData pageData) throws Exception {
  if (isSuite(pageData))
    includeSuiteSetupPage(pageData);
  includeSetupPage(pageData);
}

private void includeTeardownPages(
    PageData pageData) throws Exception {
  includeTeardownPage(pageData);
  if (isSuite(pageData))
    includeSuiteTeardownPage(pageData);
}

Analyse: Die urspruengliche Funktion mischt mehrere Abstraktionsebenen, enthaelt verschachtelte Bedingungen und ist schwer zu ueberblicken. Nach der Refaktorisierung liest sich der Code wie eine Erzaehlung: "Wenn es eine Testseite ist, fuege Setup und Teardown ein, dann gib das HTML zurueck." Jede Hilfsfunktion ist kurz und tut genau eine Sache. Man kann den Code von oben nach unten lesen und versteht auf jeder Ebene, was passiert.

Funktionen sollten eine Sache tun. Sie sollten sie gut tun. Sie sollten nur diese eine Sache tun.
— Robert C. Martin, Clean Code, Kapitel 3
