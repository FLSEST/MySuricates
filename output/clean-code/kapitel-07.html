07

Fehlerbehandlung

Fehler elegant behandeln, ohne die Kernlogik zu verschleiern — mit Exceptions, dem Special Case Pattern und einer klaren Null-Vermeidungsstrategie.

Z Zusammenfassung

Fehlerbehandlung ist ein unverzichtbarer Bestandteil professioneller Softwareentwicklung. Doch Robert C. Martin warnt eindringlich davor, dass sie die eigentliche Geschaeftslogik nicht ueberlagern darf. Wenn Fehlerbehandlungscode den Algorithmus verdunkelt, haben wir etwas grundlegend falsch gemacht. Das Ziel ist Code, der sowohl robust als auch lesbar ist — und diese beiden Eigenschaften muessen kein Widerspruch sein.

Der erste und wichtigste Grundsatz lautet: Verwende Exceptions statt Fehlercodes. In aelteren Programmierparadigmen war es ueblich, dass Funktionen einen Fehlercode zurueckgeben, den der Aufrufer pruefen musste. Dieses Muster fuehrt zu tief verschachteltem Code, weil jeder Aufruf sofort von einer Fehlerpruefung gefolgt werden muss. Exceptions hingegen trennen den fehlerfreien Pfad sauber vom Fehlerbehandlungspfad. Der Algorithmus bleibt im Try-Block klar erkennbar, waehrend die Fehlerbehandlung im Catch-Block zusammengefasst wird.

Martin empfiehlt ausdruecklich die Verwendung von Unchecked Exceptions. Checked Exceptions in Java, die in der Methodensignatur deklariert werden muessen, verletzen das Open/Closed-Prinzip: Eine Aenderung in einer tiefen Methode erzwingt Anpassungen in allen aufrufenden Methoden bis hinauf zur obersten Ebene. Unchecked Exceptions vermeiden diese Kaskade und halten die Schnittstellen sauber.

Ein weiterer zentraler Punkt ist die Bereitstellung von Kontext. Jede Exception sollte genug Information enthalten, um den Fehler lokalisieren und verstehen zu koennen. Dazu gehoeren die fehlgeschlagene Operation, der Typ des Fehlers und relevante Kontextdaten. Eine generische Meldung wie "Fehler aufgetreten" ist wertlos — eine praezise Nachricht wie "Verbindung zur Datenbank 'orders' auf Host 'db.prod.internal:5432' fehlgeschlagen nach 3 Versuchen" erlaubt dagegen eine schnelle Diagnose.

Martin betont besonders zwei Regeln zum Umgang mit Null: Gib niemals null zurueck und uebergib niemals null als Argument. Methoden, die null zurueckgeben, zwingen jeden Aufrufer zu einer Null-Pruefung — und eine einzige vergessene Pruefung fuehrt zu einer NullPointerException. Stattdessen sollte man leere Collections zurueckgeben, das Special Case Pattern anwenden oder eine Exception werfen. Ebenso sollte null niemals als Parameter uebergeben werden, weil es die aufgerufene Methode zwingt, mit einem undefinierten Zustand umzugehen.

Das Special Case Pattern (auch Null Object Pattern genannt) ist eine elegante Alternative zu Null-Pruefungen. Anstatt null zurueckzugeben, liefert man ein Objekt, das ein standardmaessiges oder neutrales Verhalten implementiert. Der Client-Code kann dieses Objekt wie ein normales Ergebnis verwenden, ohne Sonderfaelle abfangen zu muessen. Dies reduziert die Komplexitaet und eliminiert ganze Klassen von Fehlern.

Schliesslich raet Martin dazu, die Try-Catch-Finally-Struktur zuerst zu schreiben. Wenn man mit Code beginnt, der Exceptions werfen kann, definiert man zuerst den Try-Block und legt fest, was im Fehlerfall passieren soll. Dies ist eine Form von TDD fuer Fehlerbehandlung: Man schreibt zuerst den Test fuer den Fehlerfall, dann den Code, der die Exception wirft, und schliesslich den Handler. So stellt man sicher, dass die Fehlerbehandlung von Anfang an Teil des Designs ist und nicht nachtraeglich angefuegt wird.

Die uebergreifende Botschaft dieses Kapitels: Fehlerbehandlung ist eine eigene Aufgabe, die getrennt von der Geschaeftslogik betrachtet und implementiert werden sollte. Code, der diese Trennung respektiert, ist sowohl zuverlaessiger als auch leichter zu warten.

K Kernaussagen

1

Exceptions statt Return-Codes

Fehlercodes fuehren zu verschachteltem Code und erzwingen sofortige Pruefungen. Exceptions trennen den Normalpfad sauber von der Fehlerbehandlung und machen den Algorithmus lesbar.

2

Null vermeiden — weder zurueckgeben noch uebergeben

Jede Null-Rueckgabe ist eine potenzielle NullPointerException. Stattdessen leere Collections, das Special Case Pattern oder Exceptions verwenden. Null als Parameter ist ebenso zu vermeiden.

3

Try-Catch-Finally zuerst schreiben

Beginne mit der Fehlerbehandlungsstruktur, bevor du die Geschaeftslogik implementierst. Das stellt sicher, dass Fehlerfaelle von Anfang an im Design beruecksichtigt werden.

4

Special Case Pattern anwenden

Anstatt null zurueckzugeben, ein Objekt mit neutralem Standardverhalten liefern. Der Client-Code wird einfacher und Null-Pruefungen entfallen vollstaendig.

5

Kontext in Exceptions bereitstellen

Fehlermeldungen muessen genug Informationen enthalten, um den Fehler zu lokalisieren: Operation, Fehlertyp und relevante Daten. Generische Meldungen sind wertlos.

6

Unchecked Exceptions bevorzugen

Checked Exceptions verletzen das Open/Closed-Prinzip und erzwingen Aenderungskaskaden durch alle Aufrufebenen. Unchecked Exceptions halten Schnittstellen sauber und flexibel.

</> Codebeispiel

Vergleich: Fehlerbehandlung mit Return-Codes versus Exceptions und dem Special Case Pattern.

Schlecht Fehlercodes und Null-Pruefungen ueberall 
public class DeviceController {

    public void sendShutDown() {
        DeviceHandle handle = getHandle(DEV1);
        // Null-Pruefung nach Null-Pruefung...
        if (handle != DeviceHandle.INVALID) {
            DeviceRecord record = retrieveDeviceRecord(handle);
            if (record.getStatus() != DEVICE_SUSPENDED) {
                pauseDevice(handle);
                clearDeviceWorkQueue(handle);
                closeDevice(handle);
            } else {
                logger.log("Device suspended. Unable to shut down.");
            }
        } else {
            logger.log("Invalid handle for: " + DEV1.toString());
        }
    }

    // Jede Methode gibt null oder Fehlercodes zurueck
    private DeviceHandle getHandle(DeviceID id) {
        // ... kann DeviceHandle.INVALID zurueckgeben
    }
}
Sauber Exceptions und Special Case Pattern 
public class DeviceController {

    // Der Algorithmus ist klar erkennbar
    public void sendShutDown() {
        try {
            tryToShutDown();
        } catch (DeviceShutDownError e) {
            logger.log(e);
        }
    }

    private void tryToShutDown() throws DeviceShutDownError {
        DeviceHandle handle = getHandle(DEV1);
        DeviceRecord record = retrieveDeviceRecord(handle);

        pauseDevice(handle);
        clearDeviceWorkQueue(handle);
        closeDevice(handle);
    }

    // Wirft Exception statt null/Fehlercode zurueck
    private DeviceHandle getHandle(DeviceID id) {
        // ...
        throw new DeviceShutDownError(
            "Invalid handle for: " + id.toString()
        );
    }
}

// Special Case Pattern: Statt null eine leere Expense-Liste
public class MealExpenses {
    // Statt null pruefungen...
    public List<Expense> getExpenses() {
        // Gibt IMMER eine Liste zurueck — niemals null
        if (noExpensesFound) {
            return Collections.emptyList();
        }
        return expenses;
    }
}

// Oder ein Special Case Objekt:
public class PerDiemMealExpenses implements MealExpenses {
    // Standardverhalten fuer den Fall "keine Ausgaben"
    public int getTotal() {
        return getPerDiemDefault();
    }
}

"Fehlerbehandlung ist wichtig, aber wenn sie die Logik verdunkelt, ist sie falsch."
