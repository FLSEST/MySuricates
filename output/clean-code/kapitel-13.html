13

Nebenlaeufigkeit

Warum nebenlaeufige Programmierung so schwer ist und welche Prinzipien dabei helfen, sauberen und korrekten Code zu schreiben.

# Zusammenfassung

Nebenlaeufigkeit ist eines der schwierigsten Themen in der Softwareentwicklung. Robert C. Martin beginnt dieses Kapitel mit einer klaren Warnung: Nebenlaeufigen Code korrekt zu schreiben ist ausserordentlich schwer, selbst fuer erfahrene Entwickler. Ein Programm, das in einer einzelnen Thread-Umgebung einwandfrei funktioniert, kann in einer nebenlaeufigen Umgebung auf unzaehlige Weisen versagen. Die Fehler sind oft nicht reproduzierbar, schwer zu diagnostizieren und koennen jahrelang unentdeckt bleiben.

Warum benoetigen wir ueberhaupt Nebenlaeufigkeit? Der Hauptgrund ist die Entkopplung von Was und Wann. In einem sequentiellen Programm ist die Reihenfolge der Ausfuehrung klar definiert. Nebenlaeufigkeit ermoeglicht es uns, die zeitliche Kopplung aufzubrechen. Dies verbessert sowohl den Durchsatz als auch die Strukturen unserer Anwendungen. Ein Webserver, der gleichzeitig tausende Anfragen bearbeiten kann, ist ein klassisches Beispiel. Ohne Nebenlaeufigkeit muesste jede Anfrage warten, bis die vorherige abgeschlossen ist.

Martin raumt mit verbreiteten Mythen und Missverstaendnissen auf. Nebenlaeufigkeit macht Code nicht automatisch schneller — manchmal sogar langsamer durch den Overhead der Thread-Verwaltung. Das Design aendert sich grundlegend, wenn Nebenlaeufigkeit eingefuehrt wird. Die Probleme von Nebenlaeufigkeit zu verstehen ist nicht trivial, selbst wenn man Container wie Web-Container oder Applikationsserver verwendet. Nebenlaeufigkeit bringt immer zusaetzliche Komplexitaet mit sich, unabhaengig davon, wie elegant die Loesung erscheint.

Die groessten Herausforderungen liegen im Umgang mit gemeinsamen Daten. Wenn mehrere Threads gleichzeitig auf dieselben Daten zugreifen und mindestens einer davon schreibt, entsteht eine sogenannte Race Condition. Das Ergebnis haengt von der zufaelligen Reihenfolge der Thread-Ausfuehrung ab. Deadlocks, bei denen sich Threads gegenseitig blockieren, und Livelocks, bei denen Threads zwar aktiv sind, aber keinen Fortschritt machen, sind weitere typische Probleme.

Martin stellt mehrere Prinzipien vor, um Nebenlaeufigkeit beherrschbar zu machen. Das Single-Responsibility-Prinzip gilt auch fuer Threads: Nebenlaeufiger Code sollte von anderem Code getrennt werden. Datenbereiche, auf die mehrere Threads zugreifen, sollten so weit wie moeglich eingeschraenkt werden. Anstatt Daten zwischen Threads zu teilen, sollten Kopien verwendet werden, die jeder Thread unabhaengig bearbeiten kann. Threads sollten so unabhaengig wie moeglich gestaltet werden — idealerweise teilen sie ueberhaupt keine Daten.

Ein zentrales Thema sind die Ausfuehrungsmodelle der Nebenlaeufigkeit. Martin erklaert das Producer-Consumer-Muster, bei dem Erzeuger Daten in eine Warteschlange stellen und Verbraucher sie entnehmen. Das Readers-Writers-Problem behandelt den Fall, dass viele Leser gleichzeitig zugreifen koennen, Schreiber aber exklusiven Zugriff benoetigen. Das Dining-Philosophers-Problem illustriert die Gefahr von Deadlocks bei konkurrierendem Ressourcenzugriff.

Synchronized-Bereiche sollten so klein wie moeglich gehalten werden. Jeder synchronisierte Block ist ein potenzieller Engpass und kann die Leistung drastisch reduzieren. Grossflaechiges Locking fuehrt zu Problemen: entweder Performance-Verlust oder erhoehte Deadlock-Gefahr. Martin betont auch, dass korrektes Herunterfahren nebenlaeufiger Systeme ueberraschend schwierig ist und von Anfang an geplant werden muss.

Schliesslich widmet sich Martin dem Testen von nebenlaeufigem Code. Er empfiehlt, sporadische Fehler nicht zu ignorieren — sie sind oft Anzeichen fuer Nebenlaeufigkeitsprobleme. Code sollte zuerst ohne Nebenlaeufigkeit zum Laufen gebracht werden. Verschiedene Konfigurationen von Threads und Prozessoren sollten getestet werden. Instrumentierung des Codes (durch Einfuegen von sleep, yield und priority-Aenderungen) kann helfen, versteckte Fehler aufzudecken.

! Wichtige Erkenntnisse

Nebenlaeufigkeit ist komplex

Selbst einfache Programme koennen unvorhersehbare Fehler zeigen, wenn sie nebenlaeufig ausgefuehrt werden. Fehler sind oft nicht reproduzierbar und treten nur unter Last auf.

SRP auch fuer Threads

Nebenlaeufiger Code sollte strikt von Geschaeftslogik getrennt werden. Das Single-Responsibility-Prinzip gilt auf Thread-Ebene genauso wie auf Klassenebene.

Gemeinsame Daten minimieren

Je weniger Daten zwischen Threads geteilt werden, desto weniger Fehlerquellen gibt es. Verwende Kopien statt gemeinsamer veraenderbarer Objekte.

Ausfuehrungsmodelle kennen

Producer-Consumer, Readers-Writers und Dining Philosophers sind grundlegende Muster, die jeder Entwickler verstehen sollte, um Nebenlaeufigkeitsprobleme zu erkennen.

Gruendlich testen

Sporadische Fehler niemals ignorieren. Nebenlaeufigen Code mit verschiedenen Thread-Zahlen und Konfigurationen testen. Instrumentierung hilft, versteckte Bugs aufzudecken.

Synchronized klein halten

Synchronisierte Bereiche so kurz wie moeglich gestalten. Grossflaechiges Locking fuehrt zu Performance-Problemen oder erhoehter Deadlock-Gefahr.

<> Codebeispiel

Schlecht: Gemeinsamer veraenderbarer Zustand 
public class UserCounter {
    private int count = 0;

    // GEFAEHRLICH: Mehrere Threads
    // aendern denselben Zustand!
    public void increment() {
        count++;  // Nicht atomar!
    }

    public int getCount() {
        return count;
    }
}

// Verwendung: Race Condition!
UserCounter counter = new UserCounter();
for (int i = 0; i < 10; i++) {
    new Thread(() -> {
        for (int j = 0; j < 1000; j++) {
            counter.increment();
        }
    }).start();
}
// Ergebnis: Fast nie 10000!
// count++ besteht aus LESEN, ERHOEHEN,
// SCHREIBEN — drei separate Operationen.
Sauber: Thread-sichere Implementierung 
public class UserCounter {
    private final AtomicInteger count =
        new AtomicInteger(0);

    // SICHER: AtomicInteger garantiert
    // atomare Operationen
    public void increment() {
        count.incrementAndGet();
    }

    public int getCount() {
        return count.get();
    }
}

// Alternative: Unveraenderliche Daten
public class ImmutableCounter {
    private final int count;

    public ImmutableCounter(int count) {
        this.count = count;
    }

    // Neue Instanz statt Mutation
    public ImmutableCounter increment() {
        return new ImmutableCounter(
            this.count + 1
        );
    }

    public int getCount() {
        return count;
    }
}

Erklaerung

Der Operator count++ ist nicht atomar — er besteht aus Lesen, Erhoehen und Schreiben. Wenn zwei Threads gleichzeitig lesen, geht ein Inkrement verloren. Die saubere Loesung verwendet entweder AtomicInteger fuer atomare Operationen oder unveraenderliche Objekte, die bei jeder Aenderung eine neue Instanz erzeugen. Unveraenderliche Objekte sind von Natur aus thread-sicher, da sie nach der Erstellung nicht mehr veraendert werden koennen.

„Nebenlaeufigkeit ist eine Entkopplungsstrategie. Sie hilft uns, das Was von dem Wann zu entkoppeln. In Single-Thread-Anwendungen sind Was und Wann so eng miteinander verknuepft, dass der Zustand der gesamten Anwendung oft allein durch Betrachten des Stack Backtrace bestimmt werden kann.“

— Robert C. Martin, Clean Code, Kapitel 13

~ Ausfuehrungsmodelle im Detail

Producer-Consumer (Erzeuger-Verbraucher)

Ein oder mehrere Erzeuger-Threads stellen Arbeit in eine begrenzte Warteschlange. Ein oder mehrere Verbraucher-Threads entnehmen Arbeit und verarbeiten sie. Die Warteschlange dient als Puffer und entkoppelt Erzeugungs- und Verarbeitungsgeschwindigkeit. Signalisierung ueber volle/leere Queue ist entscheidend.

Readers-Writers (Leser-Schreiber)

Viele Leser koennen gleichzeitig auf eine gemeinsame Ressource zugreifen, aber Schreiber benoetigen exklusiven Zugriff. Die Herausforderung liegt in der Balance: Werden Leser bevorzugt, kann ein Schreiber verhungern. Werden Schreiber bevorzugt, sinkt der Durchsatz fuer Leser. ReadWriteLock bietet hier eine elegante Loesung.

Dining Philosophers (Speisende Philosophen)

Fuenf Philosophen sitzen an einem runden Tisch mit fuenf Gabeln. Jeder braucht zwei Gabeln zum Essen. Wenn alle gleichzeitig die linke Gabel nehmen, hat keiner zwei Gabeln — ein Deadlock. Dieses klassische Problem illustriert, wie konkurrierende Prozesse sich gegenseitig blockieren koennen.
