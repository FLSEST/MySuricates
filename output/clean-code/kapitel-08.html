08

Grenzen

Drittanbieter-Code sauber integrieren durch Kapselung, Learning Tests und klar definierte Schnittstellen an den Grenzen unseres Systems.

Z Zusammenfassung

Software existiert selten in vollstaendiger Isolation. In fast jedem Projekt muessen wir fremden Code integrieren — sei es eine Drittanbieter-Bibliothek, ein Open-Source-Framework oder eine API, die von einem anderen Team bereitgestellt wird. Robert C. Martin widmet sich in diesem Kapitel der Frage, wie wir diese Grenzen zwischen unserem Code und fremdem Code sauber gestalten koennen.

Das grundlegende Problem: Drittanbieter-Code ist nicht unter unserer Kontrolle. Der Anbieter kann Schnittstellen aendern, veraltete Methoden entfernen oder das Verhalten in neuen Versionen anpassen. Wenn unser Code direkt und ueberall an diese fremden APIs gekoppelt ist, breiten sich Aenderungen unkontrolliert durch unser gesamtes System aus. Die Loesung besteht darin, Grenzen klar zu definieren und fremden Code zu kapseln.

Martin schlaegt das Wrapper-Pattern vor: Anstatt eine Drittanbieter-Klasse direkt zu verwenden, erstellen wir eine eigene Klasse, die die fremde API kapselt und nur die fuer uns relevanten Methoden exponiert. Ein Beispiel: Wenn wir java.util.Map verwenden, bietet diese Klasse eine Vielzahl von Methoden — clear(), containsKey(), put(), remove() und viele mehr. Wenn unser Anwendungsfall nur das Lesen von Werten erfordert, sollten wir die Map hinter einem Interface oder einer Wrapper-Klasse verstecken, die nur die noetige Funktionalitaet bereitstellt. So verhindern wir, dass andere Teile des Codes versehentlich die Map manipulieren.

Ein besonders wertvolles Werkzeug an den Grenzen sind Learning Tests. Bevor wir fremden Code in unser Projekt integrieren, schreiben wir Tests, die das Verhalten der fremden API ueberpruefen. Diese Tests dienen nicht dazu, den fremden Code zu testen — sie dienen dazu, unser Verstaendnis des fremden Codes zu ueberpruefen. Wenn eine neue Version der Bibliothek erscheint, koennen wir die Learning Tests erneut ausfuehren und sofort sehen, ob sich das Verhalten geaendert hat. Learning Tests sind quasi kostenlos und bieten einen enormen Schutz gegen ueberraschende Aenderungen.

Martin fuehrt auch das Konzept des Adapter Patterns ein, um fremde APIs an unsere eigenen Beduerfnisse anzupassen. Der Adapter uebersetzt zwischen der Schnittstelle, die wir erwarten, und der Schnittstelle, die der Drittanbieter bereitstellt. Wenn sich die fremde API aendert, muessen wir nur den Adapter anpassen — der restliche Code bleibt unberuehrt.

Besonders interessant ist Martins Rat fuer den Fall, dass Code, den wir integrieren muessen, noch gar nicht existiert. Wenn ein anderes Team noch an einer Schnittstelle arbeitet, sollten wir nicht warten, sondern ein eigenes Interface definieren, das beschreibt, was wir von dieser Schnittstelle erwarten. Wir programmieren gegen unser eigenes Interface und erstellen spaeter einen Adapter, der unser Interface auf die tatsaechliche Implementierung abbildet. So koennen wir parallel weiterarbeiten und sind nicht blockiert.

Schliesslich betont Martin die Bedeutung von Boundary Tests — Tests, die spezifisch an den Grenzen unseres Systems angesiedelt sind. Diese Tests stellen sicher, dass die Integration korrekt funktioniert und geben uns Vertrauen bei Updates oder Migrationen. Sie bilden ein Sicherheitsnetz, das uns warnt, sobald eine Grenze bricht.

Die zentrale Lektion: Grenzen im Code verdienen besondere Aufmerksamkeit. Sie sind die Stellen, an denen unser sauberer, kontrollierter Code auf die unvorhersehbare Aussenwelt trifft. Durch Kapselung, klare Interfaces, Learning Tests und Adapter koennen wir diese Grenzen so gestalten, dass Aenderungen beherrschbar bleiben.

K Kernaussagen

1

Fremden Code kapseln

Drittanbieter-APIs niemals direkt im gesamten Code verwenden. Wrapper-Klassen erstellen, die nur die benoetigte Funktionalitaet exponieren und den Austausch erleichtern.

2

Learning Tests schreiben

Vor der Integration fremder Bibliotheken Tests schreiben, die unser Verstaendnis der API ueberpruefen. Bei Updates zeigen sie sofort, ob sich das Verhalten geaendert hat.

3

Adapter Pattern nutzen

Einen Adapter zwischen unserer erwarteten Schnittstelle und der fremden API platzieren. Bei Aenderungen muss nur der Adapter angepasst werden — der restliche Code bleibt stabil.

4

Interfaces fuer unbekannten Code definieren

Wenn eine Schnittstelle noch nicht existiert: ein eigenes Interface entwerfen und dagegen programmieren. Spaeter einen Adapter schreiben, der das Interface auf die reale Implementierung abbildet.

5

Boundary Tests implementieren

Tests gezielt an den Integrationspunkten platzieren. Sie bilden ein Sicherheitsnetz fuer Updates und Migrationen und geben Vertrauen, dass die Grenzen korrekt funktionieren.

</> Codebeispiel

Vergleich: Direkte Verwendung einer Drittanbieter-API versus gekapselter Zugriff mit Wrapper-Klasse und Adapter.

Schlecht Map direkt im gesamten Code verwenden 
// Map wird ueberall direkt verwendet — keine Kontrolle
Map<String, Sensor> sensors = new HashMap<>();

// Jeder kann die Map manipulieren
sensors.clear();  // Gefaehrlich!
sensors.remove("temperature");  // Unkontrolliert!

// Aenderung des Typs (z.B. generics) erfordert
// Aenderungen an JEDER Stelle im Code
Sensor s = sensors.get("temperature");
if (s != null) {  // Null-Pruefung noetig
    s.record(value);
}

// 30+ Stellen im Code verwenden sensors direkt
// Eine Aenderung der Map-API betrifft alle Stellen
Sauber Gekapselte Grenze mit Wrapper-Klasse 
// Wrapper kapselt die Map — nur benoetigte Operationen
public class Sensors {
    private Map<String, Sensor> sensors = new HashMap<>();

    public Sensor getById(String id) {
        return sensors.get(id);
    }

    // Keine clear(), remove() etc. exponiert!
    // Aenderung der internen Datenstruktur betrifft
    // NUR diese Klasse
}

// Interface fuer Code, der noch nicht existiert
public interface Transmitter {
    void transmit(Frequency frequency, Stream data);
}

// Adapter verbindet unser Interface mit der realen API
public class TransmitterAdapter implements Transmitter {
    private final VendorTransmitterApi api;

    public TransmitterAdapter(VendorTransmitterApi api) {
        this.api = api;
    }

    @Override
    public void transmit(Frequency frequency, Stream data) {
        // Uebersetzung auf die Vendor-API
        api.send(frequency.toHertz(), data.toBytes());
    }
}

// Learning Test: Unser Verstaendnis der API ueberpruefen
@Test
public void testLog4jLogging() {
    Logger logger = Logger.getLogger("MyLogger");
    logger.addAppender(new ConsoleAppender(
        new PatternLayout("%p %t %m%n"),
        ConsoleAppender.SYSTEM_OUT
    ));
    logger.info("Hello Log4j");
    // Wenn dieses Verhalten sich in einer neuen Version
    // aendert, schlaegt dieser Test sofort fehl
}

"Interessanter Code entsteht an den Grenzen. Aenderungen sind eine der groessten Gefahren an diesen Stellen. Gutes Software-Design passt sich an Aenderungen an, ohne grosse Investitionen und Nacharbeit."

— Robert C. Martin, Clean Code, Kapitel 8
