14

Schrittweise Verfeinerung

Ein detailliertes Beispiel fuer die Kunst des inkrementellen Refactorings — vom funktionierenden Prototyp zum sauberen Code.

# Zusammenfassung

Kapitel 14 ist das laengste Kapitel in Clean Code und bietet ein umfassendes, praxisnahes Beispiel fuer schrittweises Refactoring. Robert C. Martin nimmt den Leser mit auf eine Reise durch die Entwicklung eines Kommandozeilen-Argument-Parsers (Args). Dieses Kapitel ist kein theoretischer Vortrag, sondern eine detaillierte Fallstudie, die zeigt, wie sauberer Code durch Disziplin und inkrementelle Verbesserung entsteht.

Martin beginnt mit der fertigen, sauberen Version des Args-Parsers. Der Leser sieht zuerst das Ergebnis: eine elegante Klasse mit klaren Verantwortlichkeiten, gut benannten Methoden und einer durchdachten Architektur. Das Schema der Argumente wird als String definiert (z.B. "l,p#,d*" fuer einen Boolean, eine Ganzzahl und einen String), und die Klasse parst die Kommandozeile entsprechend. Diese Endfassung ist leicht lesbar und erweiterbar.

Dann folgt der entscheidende Teil: Martin zeigt die erste funktionierende Version, die alles andere als sauber war. Diese urspruengliche Implementierung enthielt lange Methoden, verschachtelte Bedingungen, duplizerten Code und unklare Variablennamen. Sie funktionierte — aber sie war ein Alptraum fuer die Wartung. Martin gibt ehrlich zu, dass diese Art von Code haeufig in der Praxis entsteht, wenn man unter Zeitdruck arbeitet und sich auf die Funktionalitaet konzentriert.

Der Kern des Kapitels zeigt den Refactoring-Prozess in kleinen Schritten. Martin demonstriert, wie man den chaotischen Code Stueck fuer Stueck in die saubere Endversion ueberfu ehrt. Jeder Refactoring-Schritt ist klein genug, dass die Tests danach immer noch bestehen. Er extrahiert Methoden, benennt Variablen um, fuehrt Interfaces ein, zerlegt grosse Klassen in kleinere und eliminiert Duplikate. Nie aendert er mehr als eine Sache gleichzeitig.

Ein fundamentales Prinzip dieses Kapitels lautet: „Erst zum Laufen bringen, dann sauber machen.“ Martin argumentiert, dass es sinnvoller ist, zuerst eine funktionierende Loesung zu erstellen und diese dann zu verbessern, als von Anfang an die perfekte Architektur zu planen. Der Schluessel liegt darin, den zweiten Schritt — das Aufraumen — nicht auszulassen. Viele Entwickler hoeren nach dem ersten Schritt auf und lassen den schmutzigen Code stehen. Das ist der Weg zu technischen Schulden.

Tests als Sicherheitsnetz spielen eine zentrale Rolle. Ohne eine umfassende Testsuite waere das schrittweise Refactoring ein Gluecksspiel. Martin schreibt Tests fuer jeden Argumenttyp und jede Fehlersituation, bevor er mit dem Refactoring beginnt. Nach jedem kleinen Refactoring-Schritt fuehrt er alle Tests aus. Wenn ein Test fehlschlaegt, macht er den letzten Schritt rueckgaengig und versucht einen anderen Ansatz. Die Tests geben ihm das Vertrauen, den Code aggressiv umzubauen.

Martin betont die Kosten des Nicht-Refactorings. Code, der nicht regelmaessig verbessert wird, verfault. Jede neue Funktion, die zu schmutzigem Code hinzugefuegt wird, macht ihn noch schmutziger. Die Entwicklungsgeschwindigkeit sinkt exponentiell. Irgendwann wird der Code so unverstaendlich, dass ein komplettes Neuschreiben die einzige Option zu sein scheint — was fast immer scheitert, weil das Wissen ueber die Anforderungen im alten Code steckt.

Das Kapitel lehrt Disziplin und Geduld. Refactoring ist keine Aufgabe, die man am Wochenende erledigt. Es ist eine taegliche Praxis, die in jeden Entwicklungszyklus integriert werden muss. Martin vergleicht es mit dem Aufraemen einer Kueche: Wer nach jedem Kochen aufraeumt, hat immer eine saubere Kueche. Wer das Aufraumen aufschiebt, steht irgendwann vor einem ueberwaeeltigenden Chaos. Die Pfadfinderregel — „Hinterlasse den Code sauberer, als du ihn vorgefunden hast“ — ist die Essenz dieses Kapitels.

! Wichtige Erkenntnisse

Erst funktionieren, dann refaktorisieren

Schreibe zuerst Code, der funktioniert. Dann mache ihn sauber. Aber ueberspringe den zweiten Schritt niemals — sonst entstehen technische Schulden.

Kleine Schritte

Jeder Refactoring-Schritt sollte so klein sein, dass danach alle Tests bestehen. Niemals mehr als eine Sache gleichzeitig aendern.

Tests als Sicherheitsnetz

Ohne umfassende Tests ist Refactoring ein Gluecksspiel. Tests geben das Vertrauen, Code aggressiv umzubauen, ohne die Funktionalitaet zu brechen.

Disziplin beim Refactoring

Refactoring ist keine einmalige Aktion, sondern eine taegliche Praxis. Die Pfadfinderregel anwenden: Code immer sauberer hinterlassen als vorgefunden.

Inkrementelle Verbesserung

Grosse Umbauten scheitern haeufig. Stattdessen den Code bei jeder Beruehrung ein wenig verbessern. Ueber die Zeit entsteht so eine saubere Codebasis.

Kosten des Nicht-Refactorings

Schmutziger Code verlangsamt die Entwicklung exponentiell. Jede neue Funktion auf schmutzigem Code macht alles schlimmer. Regelmaessiges Aufraumen ist Pflicht.

<> Codebeispiel: Args-Parser

Erste Version: Chaotisch 
public class Args {
    private String schema;
    private String[] args;
    private boolean valid = true;
    private Set<Character> unexpectedArgs
        = new TreeSet<>();
    private Map<Character, Boolean> boolArgs
        = new HashMap<>();
    private Map<Character, String> stringArgs
        = new HashMap<>();
    private Map<Character, Integer> intArgs
        = new HashMap<>();
    private int currentArg;
    private char errorArgId = '\0';
    private String errorParameter = "TILT";
    private ErrorCode errorCode = ErrorCode.OK;

    // 50+ Zeilen Parse-Methode mit
    // verschachtelten if-else-Ketten
    private boolean parse() {
        if (schema.length() == 0
            && args.length == 0)
            return true;
        parseSchema();
        try {
            parseArguments();
        } catch (ArgsException e) {
            // ...viel zu viel hier...
        }
        return valid;
    }
    // Hunderte weitere Zeilen...
}
Refaktorisierte Version: Sauber 
public class Args {
    private Map<Character, ArgumentMarshaler>
        marshalers;
    private Set<Character> argsFound;
    private ListIterator<String> currentArg;

    public Args(String schema, String[] args)
            throws ArgsException {
        marshalers = new HashMap<>();
        argsFound = new HashSet<>();
        parseSchema(schema);
        parseArgumentStrings(
            Arrays.asList(args));
    }

    // Jeder Typ hat seinen Marshaler
    private interface ArgumentMarshaler {
        void set(Iterator<String> current)
            throws ArgsException;
    }

    private class BooleanMarshaler
        implements ArgumentMarshaler {
        private boolean value = false;

        public void set(Iterator<String> cur) {
            value = true;
        }
        public boolean getValue() {
            return value;
        }
    }
    // StringMarshaler, IntegerMarshaler
    // folgen demselben Muster
}

Erklaerung

Die erste Version verwendet separate Maps fuer jeden Argumenttyp (boolArgs, stringArgs, intArgs) und eine riesige Parse-Methode voller verschachtelter Bedingungen. Bei jedem neuen Typ muessten alle Methoden erweitert werden. Die refaktorisierte Version fuehrt ein ArgumentMarshaler-Interface ein. Jeder Typ implementiert dieses Interface. Zum Hinzufuegen eines neuen Typs muss nur eine neue Marshaler-Klasse erstellt werden — kein bestehender Code aendert sich. Das ist das Open/Closed-Prinzip in Aktion.

„Es ist nicht genug, Code zum Funktionieren zu bringen. Code, der funktioniert, ist oft schlecht geschrieben. Programmierer, die einfach nur funktionierenden Code schreiben, verhalten sich unprofessionell. Sie haben vielleicht Angst, dass ihnen nicht genug Zeit bleibt, den Code zu verbessern. Ich bin anderer Meinung. Nichts hat einen tiefgreifenderen und langfristigeren negativen Einfluss auf ein Entwicklungsprojekt als schlechter Code.“

— Robert C. Martin, Clean Code, Kapitel 14

1 Der Refactoring-Prozess

1

Funktionierende Loesung erstellen

Schreibe den Code, der die Anforderung erfuellt. Hier zaehlt nur die Korrektheit, nicht die Eleganz. Teste gruendlich.

2

Tests schreiben

Umfassende Tests fuer alle Faelle erstellen: Normalfall, Randfaelle, Fehlerfaelle. Diese Tests sind das Sicherheitsnetz fuer alle folgenden Schritte.

3

Kleine Verbesserungen anwenden

Eine Methode extrahieren, eine Variable umbenennen, eine Bedingung vereinfachen. Immer nur eine Aenderung, dann Tests ausfuehren.

4

Strukturelle Aenderungen vornehmen

Interfaces einfuehren, Klassen aufteilen, Vererbungshierarchien erstellen. Groessere Umbauten, aber jeder Zwischenschritt ist testbar.

5

Ergebnis ueberpruefen

Alle Tests laufen gruen. Der Code ist lesbar, erweiterbar und folgt den SOLID-Prinzipien. Die Architektur spiegelt die Fachdomaene wider.
