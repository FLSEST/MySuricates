02

Bedeutungsvolle Namen

Warum die Wahl guter Namen die wichtigste Einzelmassnahme fuer lesbaren Code ist und welche Regeln dabei helfen.

# Zusammenfassung

Namen sind allgegenwaertig in Software. Wir benennen Variablen, Funktionen, Argumente, Klassen, Pakete, Quelldateien, Verzeichnisse, JAR-Dateien, WAR-Dateien und EAR-Dateien. Wir benennen so viel, dass wir es besser gut machen sollten. In diesem Kapitel legt Robert C. Martin eine Reihe einfacher, aber wirkungsvoller Regeln fuer die Namensgebung dar, die die Lesbarkeit und Wartbarkeit von Code dramatisch verbessern koennen.

Die erste und wichtigste Regel lautet: Namen sollen die Absicht offenbaren. Der Name einer Variable, Funktion oder Klasse soll beantworten, warum sie existiert, was sie tut und wie sie verwendet wird. Wenn ein Name einen Kommentar erfordert, offenbart er die Absicht nicht. Statt int d; // vergangene Zeit in Tagen sollte man int elapsedTimeInDays; schreiben. Der zusaetzliche Tippaufwand ist minimal, der Gewinn an Verstaendlichkeit enorm.

Desinformation vermeiden ist die zweite Regel. Programmierer muessen es vermeiden, falsche Hinweise zu geben, die die Bedeutung des Codes verschleiern. Zum Beispiel sollte man eine Gruppierung von Konten nicht accountList nennen, wenn es sich nicht tatsaechlich um eine List handelt. Besser waere accountGroup oder einfach accounts. Aehnlich aussehende Namen fuer grundlegend verschiedene Dinge sind ebenfalls desinformierend.

Bedeutungsvolle Unterscheidungen treffen heisst, dass Nummernserien (a1, a2, a3) und Noise-Woerter (Info, Data, the) keine sinnvollen Unterscheidungen schaffen. Was ist der Unterschied zwischen ProductInfo und ProductData? Oder zwischen getActiveAccount(), getActiveAccounts() und getActiveAccountInfo()? Solche Namen zwingen den Leser, den Unterschied aus dem Kontext zu erschliessen.

Aussprechbare Namen verwenden: Wenn man einen Namen nicht aussprechen kann, kann man ihn nicht ohne laecherlich zu klingen diskutieren. Statt genymdhms (generation date, year, month, day, hour, minute, second) sollte man generationTimestamp verwenden. Aussprechbare Namen machen Code-Reviews und Teamdiskussionen wesentlich einfacher.

Suchbare Namen verwenden: Einbuchstabige Namen und numerische Konstanten sind in einem grossen Code-Koerper schwer zu finden. Der Name e ist eine denkbar schlechte Wahl fuer eine Variable, da er der haeufigste Buchstabe in der englischen Sprache ist und in fast jeder Textpassage vorkommt. Die Laenge eines Namens sollte der Groesse seines Gueltigkeitsbereichs entsprechen: Je weiter der Scope, desto laenger und beschreibender der Name.

Kodierungen vermeiden: Die ungarische Notation und aehnliche Praefixe wie m_ fuer Member-Variablen sind Relikte aus einer Zeit, als Compiler und IDEs weniger leistungsfaehig waren. Heute liefern moderne Entwicklungsumgebungen Typinformationen sofort. Praefixe machen Namen laenger und schwerer lesbar, ohne einen nennenswerten Informationsgewinn. Interfaces sollten nicht mit einem I-Praefix versehen werden — besser ist es, die Implementierung zu kennzeichnen (z.B. ShapeFactory und ShapeFactoryImpl).

Klassen und Methoden benennen: Klassen und Objekte sollten Substantive oder Substantiv-Phrasen als Namen haben (Customer, WikiPage, Account, AddressParser). Methoden sollten Verben oder Verb-Phrasen haben (postPayment, deletePage, save). Zugriffsmethoden, Mutatoren und Praedikate sollten nach dem JavaBeans-Standard mit get, set und is prefixed werden.

Kontextbezug herstellen: Die meisten Namen sind nicht selbsterklaerend. Man muss sie in einen Kontext setzen — durch gut benannte Klassen, Funktionen oder Namensraeume. Variablen wie firstName, lastName, street, city, state gehoeren offensichtlich zu einer Adresse. Aber wenn man nur state allein in einer Methode sieht, ist der Kontext unklar. Durch Einbettung in eine Address-Klasse wird der Kontext sofort deutlich.

Abschliessend warnt Martin davor, unnuetzen Kontext hinzuzufuegen. Wenn eine Anwendung "Gas Station Deluxe" heisst, ist es nicht sinnvoll, jede Klasse mit dem Praefix GSD zu versehen. Kuerzere Namen sind generell besser als laengere — solange sie klar bleiben. Der Name accountAddress und customerAddress sind gute Instanznamen fuer eine Address-Klasse, aber schlechte Klassennamen.

! Wichtige Erkenntnisse

Absicht offenbaren

Jeder Name soll ohne zusaetzlichen Kommentar verraten, warum die Variable existiert, was sie enthaelt und wofuer sie genutzt wird.

Desinformation vermeiden

Keine falschen Hinweise geben. Nicht accountList nennen, wenn es keine List ist. Aehnliche Namen fuer verschiedene Dinge sind gefaehrlich.

Aussprechbar und suchbar

Namen muessen in Gespraechen verwendbar und im Code per Suche auffindbar sein. Einbuchstabige Namen nur in minimalen Scopes.

Keine Kodierungen

Ungarische Notation, Member-Praefixe und Interface-Praefixe sind ueberholt. Moderne IDEs machen sie ueberfluessig.

Klassen = Substantive

Klassennamen sind Substantive (Customer, Account), Methodennamen sind Verben (save, delete, calculate). Konsistenz ist entscheidend.

Kontext statt Praefixe

Klassen und Namensraeume geben Kontext. Unnoetige Praefixe wie GSD (Gas Station Deluxe) vor jeder Klasse vermeiden.

<> Codebeispiel: Schlechte vs. Gute Namen

Schlechte Namen 
public class DtaRcrd102 {
  private Date d;          // was ist d?
  private String nm;       // Name?
  private int st;          // Status? State?
  private String[] strArr; // welche Strings?

  public int calc() {      // was wird berechnet?
    int x = 0;
    for (String s : strArr) {
      if (s.length() > 5)
        x++;
    }
    return x;
  }

  public void proc() {     // was wird verarbeitet?
    if (st == 1) { /* ... */ }
    else if (st == 2) { /* ... */ }
  }
}
Gute Namen 
public class EmployeeRecord {
  private Date hireDate;
  private String fullName;
  private EmploymentStatus status;
  private String[] qualifications;

  public int countLongQualifications() {
    int count = 0;
    for (String qualification : qualifications) {
      if (qualification.length() > MIN_LENGTH)
        count++;
    }
    return count;
  }

  public void processStatusChange() {
    if (status == EmploymentStatus.ACTIVE) {
      /* ... */
    } else if (status == EmploymentStatus.ON_LEAVE) {
      /* ... */
    }
  }
}

Analyse: Im schlechten Beispiel muss der Leser raten, was DtaRcrd102 ist, was d und st bedeuten, und was calc() berechnet. Im sauberen Beispiel ist sofort klar: Es handelt sich um einen Mitarbeiterdatensatz, wir zaehlen lange Qualifikationen, und der Status wird ueber ein Enum abgebildet statt ueber magische Zahlen. Jeder Name traegt zur Verstaendlichkeit bei.

Der Name einer Variable, Funktion oder Klasse sollte alle grossen Fragen beantworten. Er sollte verraten, warum sie existiert, was sie tut und wie sie verwendet wird.
— Robert C. Martin, Clean Code, Kapitel 2
