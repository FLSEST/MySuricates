Kapitel 4

Kommentare

Wann Kommentare helfen, wann sie schaden und warum guter Code sich selbst erklärt.

Zusammenfassung

Kommentare sind bestenfalls ein notwendiges Übel. Sie kompensieren unser Versagen, uns im Code auszudrücken. Jeder Kommentar stellt ein Versagen dar, den Code selbstsprechend zu gestalten. Bevor Sie einen Kommentar schreiben, fragen Sie sich: Kann ich den Code so umstrukturieren, dass der Kommentar überflüssig wird?

Es gibt durchaus gute Kommentare: rechtliche Hinweise, informative Kommentare die reguläre Ausdrücke erklären, TODO-Kommentare die auf zukünftige Aufgaben hinweisen und Warnungen vor Konsequenzen. Diese dienen einem echten Zweck und helfen dem Leser.

Schlechte Kommentare hingegen sind Legion: redundante Kommentare die nur wiederholen was der Code schon sagt, irreführende Kommentare die nicht mehr zur Realität passen, auskommentierter Code der wie ein Geschwür im Quelltext sitzt. Die Versionskontrolle merkt sich alles – löschen Sie auskommentierten Code sofort.

Key Takeaways

1

Code sollte sich selbst erklären – Kommentare sind oft ein Zeichen von Schwäche im Code-Design.

2

Gute Kommentare: rechtliche Hinweise, informative Kommentare, TODOs und Warnungen vor Konsequenzen.

3

Schlechte Kommentare: redundante Kommentare, irreführende Beschreibungen und auskommentierter Code.

4

Javadoc in öffentlichen APIs ist sinnvoll – in internem Code ist es oft unnötiger Ballast.

5

Auskommentierten Code sofort löschen – die Versionskontrolle merkt sich alles, es gibt keinen Grund ihn zu behalten.
